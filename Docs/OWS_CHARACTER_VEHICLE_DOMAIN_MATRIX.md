# OWS Character and Vehicle Domain Reconciliation Matrix

> **Status:** Accepted Stage 3 cross-domain reconciliation contract for [Character issue #107](https://github.com/GameForgeStudio/Unreal-Open-World-Starter/issues/107) and [Vehicle issue #108](https://github.com/GameForgeStudio/Unreal-Open-World-Starter/issues/108), authorized by Aurora on 2026-08-26. It aligns two independently authoritative domain contracts; it does not create a third Character/Vehicle owner, replace the accepted Mobility contract, authorize implementation, or make any child ready for checkout.

## Purpose

The [OWS Character Architecture](OWS_CHARACTER_ARCHITECTURE.md) and [OWS Vehicle Architecture](OWS_VEHICLE_ARCHITECTURE.md) are designed in one coordinated pass because moving supports, boarding, occupancy, control handoff, animation, camera, collision, recovery, and conformance consume both public surfaces. They remain separate contracts because each domain must build, load, cook, package, and conform without the other or the Integration family.

This matrix is the shared place to detect duplicate ownership, forbidden dependencies, mismatched classifications, and incompatible public assumptions. It does not duplicate either domain's detailed capability catalog.

## Source of truth and conflict rule

Use this order when applying the three domain artifacts:

1. Aurora's latest explicit requirement.
2. The accepted contract applicable to the subject and within that contract's explicit scope, including the Platform, Shared Gameplay, Mobility, Character, Vehicle, this reconciliation matrix, and City contracts.
3. Current source, assets, and configuration for what exists today.
4. Current-state summaries and working documents.

Within the second source-of-truth tier, package-wide and Shared contracts govern their cross-product subjects, the Character and Vehicle contracts govern their owned surfaces, the Mobility contract governs relationships and transitions, and this matrix governs the seam and dependency direction. These are scopes, not a hidden precedence order. No accepted contract silently overrides another accepted contract. A real conflict returns to Aurora. Current implementation is evidence, not permission to redefine the target; target architecture is not evidence of implementation.

No Supported API may expose inherited fork-private types, require a literal `/Game` or provider asset path, or let one domain read or mutate another domain's private state.

## Coordinated change rule

A proposed Character or Vehicle change that affects the other domain must identify:

1. the authoritative owner and public contract being changed;
2. whether the peer consumes that contract directly or only through Integration;
3. independent Character-only and Vehicle-only effects;
4. combined Mobility effects and applicable matrix rows;
5. compatibility, redirect, cook, migration, and support-claim consequences; and
6. the separately accepted implementation issue that owns the change.

If those answers produce duplicate state, a private dependency, or an Integration catch-all, the change is invalid until Aurora resolves the conflict.

Every migration unit has one separately claimed issue and one immutable ledger entry that identifies the tested baseline commit/OWS/Unreal versions, current and target owner, exact source/target inventory, current and target classification, every known C++/Blueprint/hard/soft/tag/config/input/save/network/cook consumer, stable identities and revisions, protected behavior rows, compatibility mechanism, one-writer selection rule, supported source/target versions, provenance/license obligations, rollback/recovery path, deprecation/removal conditions, and required evidence. Baseline commit `393b5a34308f5bdbc8d6a52c85748e0df4405c46` is an architecture audit input; #115 remains the owner of the reproducible pre-change baseline and non-mutating guardrails.

The additive state model is `baselined -> OWS contract and conformance added -> applicable compatibility or documented source-migration mechanism available -> scoped consumers migrated -> one default authority cut over -> applicable Supported deprecation window observed or Internal/Experimental maintained-consumer retention predicate satisfied -> removal eligible`. A ledger explicitly marks an inapplicable stage and the evidence that makes it inapplicable; it never invents an adapter or a Supported semantic-version wait for a source-only or non-Supported surface. Exactly one authoritative implementation writes canonical state at every phase. A development/test-only shadow may compare immutable inputs/results but cannot mutate, replicate, persist, cook into Shipping, or become fallback authority. A cutover occurs only at a validated composition/session boundary; runtime hot-swap is not implied. Failure before cutover preserves the prior path.

Rollback authorities remain separate. Before runtime, #123 restores a failed installation transaction to the last verified matched code/content/config/profile generation. Persistence #137 discards or quarantines an uncommitted durable-data candidate and republishes the last verified checkpoint under the accepted package policy. Each domain validates its record and selected provider/profile. If a separately accepted release workflow coordinates those operations, it does not take their semantic authority. None of these mechanisms reverses committed gameplay, silently selects a provider, mixes generations, or implies an unproved downgrade or runtime hot-swap.

Character and Vehicle advance independently through that state model, and each domain's artifact, clean-host conformance, and domain-only migration claim can pass without the peer or Integration building, loading, cooking, or running. Integration declares and validates the exact public-contract combination it consumes and owns any temporary cross-domain adapter. A slice that changes a declared Integration boundary also triggers the applicable #163/#167 composed proof, but that separately owned proof neither transfers ownership nor makes the peer a dependency of the domain artifact. Arbitrary upstream-fork import and whole-domain or whole-bundle uninstall remain outside the maintained-fork, one-bundle product model and cannot be enabled by a release/profile claim. No mixed-OWS-release, downgrade, or previous-Unreal-minor claim exists unless a separately accepted release/profile contract names and passes that exact path. Optional replacement-provider disable, rollback, uninstall, and cleanup are claimed only to the extent their accepted provider contract and evidence explicitly support them.

A legacy surface becomes removal-eligible only when its ledger has zero supported consumers; source plus binary-asset, World Partition/external-actor, config/tag/input, save/schema, cook/stage, and packaged-install scans are clean; every supported upgrade chain no longer needs it or retains its accepted migrator; the Platform deprecation window applies when the old surface was Supported; an exact removal/rollback issue is claimed; and Aurora accepts that exact removal scope. Internal exposure receives no Supported semantic-version promise, but protected current behavior and maintained-content consumers still block removal until migrated and proven. A redirect, shim, or migrator has its own retention/removal evidence and never promotes the legacy surface it carries.

## Coordinated content and cook-tier contract

Content tier, semantic owner, support classification, compatibility lifecycle, and current filesystem path are independent axes. Every Unreal package must have one target owner and one target physical tier before its #121 migration child can pass. An Internal provider asset may be Runtime because a selected Supported profile requires it; use by a showcase or test never makes its path Supported. Current placement and references are migration evidence, not permission to move, rename, resave, delete, or reclassify by folder name.

| Tier | Normative role | Normal cook and dependency rule |
| --- | --- | --- |
| **Runtime** | Reusable domain, Shared, Input, or Integration behavior/data required by an explicitly packaged runtime profile, including Internal implementation and compatibility artifacts still required by advertised versions | Included only through that profile's validated closure; may follow only accepted Runtime dependency edges and cannot reference `/Game/OWS`, Showcase, Development, Editor, or Test content |
| **Showcase** | Starter-shell composition under `/Game/OWS`: canonical map/game mode/controllers, roster placement/presentation, wiring, and the six utility pads | Included only when a packaged profile selects the starter showcase; may consume Runtime/Integration public contracts, but no reusable plugin may depend on it |
| **Development** | Inherited demonstrations, engineering labs, prototypes, manual benchmarks, stress courses, reference manifestations, and evaluation content | Retained in the complete source bundle and excluded from the standard workflow and every normal/Shipping cook; an exact non-Shipping evaluation artifact may select it explicitly, and Unreal's `Development` build configuration does not select it automatically |
| **Editor** | Authoring, visualization, generation, migration, validation-preview, and editor-utility content | Lives behind its owning Editor boundary and never enters runtime cooks or staging; a generated shippable derivative is a separate Runtime package |
| **Test** | Synthetic providers, negative fixtures, golden migrations, analytic courses, and automation maps/data | Lives behind its owning Test/Validation boundary and is excluded from Shipping code, cooks, and staging; composed fixtures belong to Integration or the shell rather than either domain |

The complete one-bundle source installation retains every maintained fork, tool, Development resource, Editor resource, and Test fixture. A build declares its finite composition-profile set before cook. Its production artifact is the deterministic union of each selected profile's Runtime closure plus Showcase roots only when a profile selects the canonical starter experience. Multiple inactive providers may be packaged for different profiles, but each active profile still selects exactly one authority and provider presence never activates it. Packaging a subset is not selective installation, provider/domain uninstall, or permission to fetch an upstream dependency.

A closure includes enabled and compiled plugins/modules, selected provider roots, required configuration registrations, hard references, explicitly managed soft/Primary Assets, generated Runtime products, map/Data Layer/HLOD/World Partition external packages, and compatibility artifacts required by every advertised source version. Soft references, module type, plugin enablement, and directory names alone never prove inclusion or exclusion. A map's external actors, external objects, HLOD, and Data Layers follow that map's tier; reusable definitions it consumes retain their own Runtime owner. Configuration follows the owner and consuming profile: Runtime requirements, Showcase startup settings, and Development/Editor/Test diagnostics cannot be merged into one unscoped global truth.

Runtime and Showcase closures reaching Development, Editor, or Test content fail validation. A mixed-responsibility package remains protected in the conservative current compatibility closure until an exact #121 child separates or replaces the edge; an Editor-only package is never promoted merely to hide an invalid runtime reference. Development and Test work also preserve the accepted dependency graph: Character remains Vehicle-free, Vehicle remains Character-free, and cross-domain fixtures stay Integration/shell-owned.

Each #121 child covers one stable target owner, one tier, and one approved cohesive feature/package/config graph. It records exact roots, every dependency category, target tier/owner, redirect/fix-up/resave plan, configuration scope, provenance, before/after reference and cook manifests, rollback, and unchanged behavior. Character Runtime, Character non-Runtime, Vehicle Runtime, and Vehicle non-Runtime are minimum separations, not four monolithic migrations: create as many tight children as ownership, tier, and feature closure require. Shell Showcase, Input, Integration, Character Foley/overlay, Editor, Test, optional reset, and replacement-provider graphs retain distinct owners and independently accepted inventories; Input migration remains coordinated with #117 and future Integration content waits for #120. #122 thins the shell only after displaced responsibilities have verified owners and must preserve the canonical map and six pads. A narrow #121 child does not wait for #123; #123 later consumes the verified manifests for reviewed existing-project setup.

Missing required closure, ownerless or multiply tiered packages, unmanaged soft assets, unresolved required references, or Development/Editor/Test leakage into a normal artifact fails cook/staging. Source-installed but unselected providers must not alter another profile's closure or result. A selected missing, duplicate, incompatible, or incompletely cooked provider fails validation or startup with actionable diagnostics and never silently falls back.

## Independent conformance reconciliation

The [Character independent contract](OWS_CHARACTER_ARCHITECTURE.md#independent-conformance-contract) and [Vehicle independent contract](OWS_VEHICLE_ARCHITECTURE.md#independent-conformance-contract) are the complete domain T0 specifications required by #107/#108. Both reuse the Mobility matrix's result language and durable-record envelope, but each has its own fixtures, manifests, owners, and release result. A composed test cannot replace an independent result, and an independent synthetic-provider result cannot certify a relationship or complete Mobility behavior.

| Evidence layer | Owning responsibility | Required separation and handoff |
| --- | --- | --- |
| Character T0 | Exact Character implementation/migration child and Character Test boundary | Builds, loads, cooks, packages, and runs applicable `CHAR-BLD-001` through `CHAR-OPS-001` without Vehicle, Integration, shell, or `/Game`; `CHAR-REG-001` is excluded from T0, and synthetic peer/Shared observations prove only Character consumption/execution |
| Vehicle T0 | Exact Vehicle implementation/migration child and Vehicle Test boundary | Builds, loads, cooks, packages, and runs applicable `VEH-BLD-001` through `VEH-OPS-001` without Character, Integration, shell, or `/Game`; `VEH-REG-001` is excluded from T0, and synthetic controls/surfaces/consequences prove only Vehicle behavior and public contributions |
| Harness infrastructure | #141 | Supplies reusable runners, role orchestration, fixtures, fault injection, evidence storage, and cleanup mechanics; owns no Character/Vehicle semantics and creates no Shipping dependency |
| Composed Stage 3 release | #167, consuming accepted #141 infrastructure and exact domain/Integration results | Imports only immutable clean-commit Character/Vehicle T0 and Integration release records whose exact commit, Unreal/build/platform, public schemas, profiles/providers, configuration, content/assets, and fixture generations match the composed release candidate, then runs the applicable `MOB-*` T1–T5 combinations; a mismatch blocks or reruns the evidence, and #167 cannot mix generations, average, rewrite, or mask an independent failure |
| Protected current/composition regression | Character/Vehicle baseline plus the exact changed-domain, shell, and Integration owners; aggregated under #167 where applicable | Runs `CHAR-REG-001`, `VEH-REG-001`, and affected protected/Mobility rows before and after each slice; it is companion evidence required for a release containing the starter/full composition, not T0, and proves preserved current behavior rather than the future independent or Mobility target by itself |

Every row begins `NR` and records the exact commit, clean/dirty state, Unreal/build/platform, profile/provider/capability manifests, fixtures and versions, network/backend/impairment where claimed, repetitions, durable evidence, result, and cleanup audit. A dirty development run also records a complete source-tree/patch digest, but it cannot generate a release support manifest and must be rerun from the clean exact release-candidate commit. `PASS` applies only to the recorded combination; `FAIL` and `BLOCKED` require a tight linked issue; `N/A` requires a validator-confirmed authored capability reason. No partial pass or averaging exists. #167 accepts only clean T0/Integration release records whose generation fields match the composed candidate exactly; otherwise that record is rerun or the release remains blocked. A domain-only artifact/profile result may be recorded from T0, but final presentation as a reusable OWS domain always requires the same-generation complete-starter integration companion required by Platform; that companion never turns a peer or Integration into a T0 dependency. A generated support manifest is the intersection of applicable clean, same-generation passing evidence, never a deduction from source/content presence, an architecture statement, a representative fixture, or the other domain's result.

Standard profiles must pass with optional/Experimental providers absent. Reset-enabled Vehicle proof is required for the Supported developer-optional reset capability while reset-disabled remains the standard profile result. Experimental Character profiles, future Vehicle promotion lanes/alternative providers, multiple-profile packaging, optional-provider removal, extra platforms, and extra network roles/platforms/impairment combinations are gates only when the exact release declares them. Every advertised networked feature nevertheless passes both legacy replication and opt-in Iris under the Shared contract. Optional-lane absence never weakens or blocks the standard claim, and partial evidence never broadens it.

## Publication and implementation gate

The three artifacts are published together as internally consistent, independently authoritative Character and Vehicle domain contracts plus this shared reconciliation contract. The live issue graph must reflect these gates before either architecture issue is closed or any child is made ready.

Publication does not implement a feature, prove conformance, change current behavior, or make #150–#156 or any other child ready. Every implementation child remains separately accepted, ready, and claimed.
